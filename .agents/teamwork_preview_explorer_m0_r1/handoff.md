# Handoff Report — Multi-Tenant Audit Logging (R1)

## 1. Observation
- **In-Memory Volatility**: The existing `AuditLogService` (`src/audit/audit-log-service.ts`) uses private in-memory Maps (`this.logs` and `this.licenseLogs`):
  ```typescript
  48:   private logs: Map<string, AuditLog> = new Map();
  49:   private licenseLogs: Map<string, AuditLog[]> = new Map();
  ```
  Consequently, all logs are deleted whenever the application restarts.
- **Shared Trade Logs**: The trade auditing system `ImmutableTradeAudit` (`src/audit/immutable-trade-audit.ts`) reads and appends all log records to a single file `audit-log.jsonl` under `~/.cashclaw/` without segregating by tenant or subscriber:
  ```typescript
  58:     this.logPath = logPath ?? cashclawPath('audit-log.jsonl');
  ```
- **Tenant Context**: In other modules of the system (such as P&L tracking in `src/api/routes/subscriber-pnl-routes.ts` and `src/db/migrations/015_subscriber_attribution.sql`), tenant-isolated queries use a `subscriber_id` or `tenantId` field to separate tenant contexts. `src/raas/subscriber-tenant-isolator.ts` defines `buildTenantFilter` to generate safe SQL WHERE clauses scoped to `subscriber_id`.
- **System States**:
  - Administrative trading halts and resets are defined as Express routes in `src/api/routes/admin.ts` (handling `POST /admin/halt` and `POST /admin/resume`).
  - Automated trading stops occur in `src/risk/circuit-breaker.ts` (triggered by consecutive losses, latency spikes, or excessive volatility) and `src/risk/drawdown-monitor.ts` (triggered by daily or total portfolio drawdown thresholds).
  - License operations (created, activated, revoked, deleted) reside in `src/api/routes/license-routes.ts`.
  - Trade execution details (opportunities detected, order placements, fills, and failures) occur in `src/arbitrage/trading-loop.ts` and `src/execution/order-executor.ts`.

---

## 2. Logic Chain
1. To build a persistent and secure system, we must store audit logs in PostgreSQL instead of volatile memory Maps or shared file structures.
2. Multi-tenant isolation requires storing and indexing logs using a `tenant_id` column (mapping to `subscriber_id` or `license_id`), enabling queries to be isolated via the existing `buildTenantFilter()` design pattern.
3. Immutability necessitates a SHA-256 hash chain per tenant. The hash of a log record must depend on its preceding log entry's hash. Therefore, calculating a new entry's hash requires querying the latest entry for that specific tenant.
4. Concurrent log writes (e.g., executing multiple trade legs simultaneously) can cause race conditions where two threads retrieve the same "latest" entry, resulting in identical sequence numbers and a broken hash chain linkage.
5. To resolve concurrency conflicts, we can acquire a PostgreSQL Transactional Advisory Lock (`pg_advisory_xact_lock(hashtext(tenant_id))`) to serialize log writes *for a specific tenant* without blocking other tenants.
6. To support high-performance log querying, we must index `(tenant_id, created_at DESC)` and `(tenant_id, sequence_number DESC)`. Key-set cursor-based pagination must be utilized instead of SQL offset pagination to ensure rapid querying over millions of rows.
7. To support CSV/JSON export without exhausting Node process memory (heap overflow) during large fetches, we must stream database results line-by-line directly to the client using `pg-query-stream` and stream transformers.

---

## 3. Caveats
- **Backfill Strategy**: Prior logs in `audit-log.jsonl` are un-segregated. If legacy logs must be migrated, they will default to a placeholder tenant ID like `'legacy-tenant'` and be hashed sequentially in a separate migration script.
- **Clock Drifts**: The timestamp is generated by the application server. If server clocks drift, the sequential order of audit logs is protected by utilizing a strictly incrementing `sequence_number` (computed within the advisory lock transaction), rather than relying purely on timestamps.

---

## 4. Conclusion
We propose migrating both the licensing audit log (`AuditLogService`) and trade audit log (`ImmutableTradeAudit`) to a single Postgres-backed `tenant_audit_logs` table. Hash chain integrity is guaranteed mathematically using SHA-256, and concurrency is handled elegantly via per-tenant PostgreSQL transactional advisory locks. The REST APIs will query logs using cursor-based pagination and stream exports utilizing database cursors.

## 5. Verification Method
1. **DB Migration Test**: Run the project migrations using `npm run db:migrate` or similar commands, and confirm the `tenant_audit_logs` table is correctly created.
2. **Mathematical Chain Test**: Write unit tests that append 100 mock audit logs and verify the math of the SHA-256 hash chaining. Tamper with a row in the database and verify that the chain integrity function identifies the tampered record.
3. **Concurrency Test**: Spawn 20 parallel threads that call the logging helper for the same tenant. Verify that sequence numbers are generated continuously (from 1 to 20) with no duplicates or index gaps.
4. **Tenant Access Test**: Attempt to fetch tenant B's logs using tenant A's JWT token and verify that the endpoint returns `403 Forbidden`.
5. **Stream Export Test**: Perform a CSV export with 10,000 seeded log entries and verify that the memory consumption of the Node process remains flat (<100MB).
